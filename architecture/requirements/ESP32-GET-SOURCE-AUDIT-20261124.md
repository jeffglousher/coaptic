# Where an ESP32 GET spends work

The November 23 firmware comparison gives us two different problems. The synchronous Coaptic server was competitive for a single read. The asynchronous server consistently took longer on the seven-byte and 2,000-byte reads in the native-client rotations. A large-body copy cannot explain the seven-byte result. This audit follows those exact firmware sources and the linked Xtensa executables. [Board measurements and conditions](ESP32-LIBCOAP-HEAD-TO-HEAD-20261123.md)

## What the two implementations actually do

Core source `161a225` differs from the November 23 firmware core only in the standard-library UDP adapter. The retained C handler file matches its companion Git blob byte for byte. The source paths below refer to the release fixtures used on the Waveshare. [C server handler](https://github.com/jeffglousher/coaptic-validation/blob/2ff7dbd/tools/esphome/components/libcoap_benchmark/libcoap_benchmark.cpp#L169), [Rust handlers](https://github.com/jeffglousher/coaptic-validation/blob/1de100cc/tools/esphome/rust/src/network.rs), [async service loop](https://github.com/jeffglousher/coaptic-validation/blob/1de100cc/tools/esphome/rust/src/network/async_service.rs) and [ESP async driver](https://github.com/jeffglousher/coaptic-validation/blob/1de100cc/tools/esphome/rust/src/async_network.rs)

- **Incoming bytes.** Coaptic receives directly into a bounded RX slot. Dispatch then copies the used datagram into reusable scratch. This lets the parsed message borrow the scratch while the engine mutates or releases slots, including when opening an OSCORE message. The independent client's plain large GETs were only 12 and 14 wire bytes. Removing those copies would save 26 bytes per complete large read. The C UDP path also creates a PDU and copies input when its backing address differs from the receive buffer. Neither implementation copies 2,000 bytes on ingress to serve this GET. [Coaptic dispatch](../../src/app/mod.rs) and [scratch ownership](../../src/app/response.rs)
- **Routing.** Coaptic compares borrowed path segments against occupied entries in a fixed route table. In the tested fixture, test is the second registered handler and large is the fifth. Libcoap builds a URI path string and looks it up in a hash table. Its ordinary URI builder walks path options to determine the size and again to write the string. Hashing can help a large route table. It comes with key construction and allocator costs on a tiny one. The measurements with six registered handlers and built-in discovery do not establish a benefit from adding a hash table to Constrained. [Coaptic site dispatch](../../src/app/site.rs)
- **Outgoing bytes.** Both ordinary handlers borrow their static body. Coaptic's classic Block2 path passes the selected slice to the encoder, and can retain the encoded TX packet for duplicate replay. The 1,024-byte staging array elsewhere in the file belongs to a different path. C checks the requested block and representation length first. On the initial 2,000-byte GET, Coaptic acquires a TX slot, attempts a whole-response encode, releases the slot on the size miss and selects the first block. The encoder checks bounds before copying the oversized body. The avoidable work here is setup and retry. Any early size decision needs to preserve size-error precedence, capacity refusal, eviction and replay semantics. [Response selection](../../src/app/mod.rs), [encoder](../../src/message/encode.rs) and [prior retained-body experiment](DISPATCH-SCRATCH-20261104.md)
- **Async scheduling.** The ESP companion's service loop calls `cooperate().await` before protocol progress. Its first poll self-wakes and returns pending. The driver consumes that wake, probes native readiness if interests remain and yields to FreeRTOS every 32 root polls. The C fixture also yields every 32 I/O loop iterations. Coaptic additionally evaluates protocol deadlines at wait, progress and send boundaries. These transitions support cancellation, timer precedence and fairness. A self-wake does not imply a scheduler sleep per GET. In an earlier instrumented async development image, just 1,139 µs of 92,358 µs inside receive-return to send-entry spans lay in explicit native delays. There were zero native select calls inside those spans. Preemption, work before receive return and radio time remain separate. [Wake boundary](../../src/app/wake.rs), [send deadlines](../../src/app/async_server.rs) and [device trace boundaries](ESP32-LIBCOAP-HEAD-TO-HEAD-20261123.md)

The exact unprotected async ELF links the prepared service driver at `0x42024bec` to `poll_engine_async` at `0x4205bc0c`, which references `dispatch_rx_io_async` at `0x42084534`. The latter two symbols contain 50,883 and 90,358 bytes of code. Their Xtensa entry instructions reserve 5,632 and 14,416 bytes of local frame space. The driver reports a 10,024-byte root future. The C ELF splits work between a 137-byte datagram handler, a 1,291-byte dispatch function, a 214-byte fixture GET handler and their callees. Symbol sizes describe code organization. They cannot establish an executed instruction count, cache miss rate or peak process stack. Earlier source splits reduced Rust frame sizes and still failed the end-to-end performance test. [Code-placement experiments](LIBCOAP-SPEED-20261109.md)

## An experiment on repeated option decoding

I counted option iterator starts and yielded entries inside a real synchronous `App::poll`, using the Constrained profile with blockwise enabled, OSCORE compiled, unprotected reads and the same route order as the device. Counters were read before verifying the reply. The seven-byte read and unsolicited block zero each traversed their single Uri-Path option 13 times. The follow-up with Uri-Path and Block2 started 12 traversals and visited 20 entries. These counts exclude the initial wire validation pass.

The prototype reuses the Observe-presence bit already collected by `request_options`. For an ordinary read, that lets the dispatcher skip two further Observe searches. Requests carrying Observe and DELETE still enter the existing processing path. There is no extra cache, allocation or per-request storage. The counts fell from 13 to 11, 13 to 11 and 20 to 18 respectively. The instrumented Windows library suite passed 910 tests, including the new counting fixture. [Dispatch and Observe planning](../../src/app/mod.rs) and [option iterator](../../src/message/option.rs)

With counters removed, two distinct optimized Windows binaries each ran 20,000 verified seven-byte reads and 20,000 complete two-block reads per process. The processes used one CPU and reversed order between pairs. After a warm-up pair, the median paired elapsed-time reduction over ten pairs was 7.2% for the small read (nine pairs faster) and 5.3% for the complete blockwise read (ten faster). Median process means were 620 to 572.5 ns and 1,675 to 1,588.5 ns per read. These in-memory timings include request generation, loopback transport, dispatch and payload verification. They measure neither Wi-Fi nor ESP32 task CPU. An initial build check found two identical executables. The original was rebuilt, both hashes checked, and only distinct binaries supplied these results.

## The same change on the physical ESP32-S3

I rejected the prototype for this checkout. The two rebuilt firmware images differed in one core source file and their run IDs. They used the same async runtime, Constrained capacities, 16 KiB instruction cache, compiler settings, AES 0.9.4, unprotected service and client binaries. Their OTA images were both 1,641,536 bytes. The candidate's linked dispatch function grew by 19 bytes and retained its 14,416-byte entry frame.

Four paired boots ran in alternating order, eight boots total. Each boot served 192 native-client reads, 48 independent aiocoap reads and 32 reads from two overlapping aiocoap clients. All 2,176 reads verified. Each device recorded 368 received and 368 transmitted datagrams, zero application drops and zero wait errors. Both requests left the independent clients before the first reply in all 128 groups. The original normal firmware was restored and identified after the comparison.

For two large reads, it rose from 27.05 to 27.58 ms. The cost of finding two options is real. It does not explain the end-to-end async gap.

## What duplicate handling buys

In two additional hardware boots I sent eight distinct confirmable GETs for the seven-byte value, each followed 25 ms later by a byte-identical retransmission from the same UDP socket. Each image returned all 16 expected replies. The libcoap fixture recorded **16 handler calls and zero peer refusals**. For this resource, rerunning the C handler only fetches a static pointer. An application that computes its value would pay for that computation again. The Coaptic image recorded 16 receives, 16 sends and zero drops. It exposes no handler-call counter. The Rust source looks up an unexpired entry before dispatch and replays the stored reply when present. The counting-handler regression independently verifies one invocation for an immediate repeat in software. Coaptic permits rerunning an idempotent method when a replay is unavailable. The normal firmware identity was verified again after both boots. [Replay implementation](../../src/app/mod.rs) and [counting-handler regression](../../src/app/tests.rs)

The next high-value measurement is scheduled worker time from receive return through dispatch and reply encoding on the ordinary async GET, with time waiting for transport recorded separately. This would distinguish time in shared protocol work from the ESP adapter and from preemption. The strongest portable design candidate is to finish common synchronous request preparation before entering the part of the async operation that can wait, keeping only the state needed to resume. The matched executable and earlier failed function-splitting experiments make it important to measure actual frames, executed time and whole-device results together. Neither unprotected nor established-OSCORE original-baseline CPU target is met by this study.
